# RIWAY manual sandbox

Run from this repository with Node 22–24 and installed dependencies:

```sh
npm ci
npm run sandbox:manual
```

Open [the sandbox console](http://127.0.0.1:4682/fixture/manual) after the app is ready. The app itself runs at [127.0.0.1:4174](http://127.0.0.1:4174). Use the IP address on both ports so the browser shares the sandbox sign-in cookie. A normal and a private window can hold different roles. Stop the command and restart it to reset all test data.

The console is part of the test fixture and listens only on loopback. It uses synthetic users and an in-memory database running the repository migrations. Ordinary screens and staff forms run the app’s normal permission and database routines. The console creates orders and delivers simulated outcomes to those database routines because hosted auth and providers are disconnected. These controls send no external credentials, payments, or email. Local recordings are optional in the voice consent fixture.

To test guest checkout, sign out and request a code at **Checkout review** using `guest@example.invalid`. Refresh the console in a second tab and read **Guest verification inbox**. Try an incorrect code, then enter the current six-digit code at checkout. It expires after five minutes or five unsuccessful attempts. Open the account to verify the guest identity. Signing in with this address again uses the same synthetic account.

## Temporary online testing

The online launcher serves the same synthetic environment through one HTTPS origin. It puts an access-code screen in front of the console, the application, assets and APIs. The two app processes and the gateway bind to loopback. Browser requests for guest verification go through the protected gateway. App database calls stay on the local machine.

Start a [Cloudflare Quick Tunnel](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/) to `http://127.0.0.1:4189`. Set `RIWAY_SANDBOX_ORIGIN` to its exact HTTPS URL and set `RIWAY_SANDBOX_ACCESS_CODE` to a newly generated random URL-safe code of at least 24 characters. Run `npm run sandbox:online` from the repository. Open `/fixture/manual` on the tunnel origin and share the access code separately from the link.

To run an independent online instance alongside an existing one, use a separate checkout and set `RIWAY_SANDBOX_APP_PORT`, `RIWAY_SANDBOX_FIXTURE_PORT` and `RIWAY_SANDBOX_GATEWAY_PORT` to distinct free loopback ports. Point its Quick Tunnel to the new gateway port. The defaults are 4174, 4682 and 4189.

The tunnel depends on the machine and both processes staying online. A new Quick Tunnel has a new URL. Restarting the fixture clears the synthetic database and revokes existing access sessions.

## Membership, sponsor, compensation and reversal

1. Choose **First-time buyer**. On the distributor store, wait for the introduction to link. The seeded sponsor uses referral code `QAFIXTURE` and RIWAY member ID `QA-BROWSER`.
2. Open **Shop**, add **Synthetic membership package**, and review the current total at checkout. Try delivery and **Synthetic Manila collection centre**. Verify the package and the displayed membership terms and Code of Conduct. The real gateway checkout control stays disabled.
3. In the console, choose the membership package and collection or delivery. Try creating an order without the membership checkbox to see the refusal, then accept both synthetic agreements and select **Create pending order**. Open the order from **Orders**. Confirm the frozen package, total, fulfilment choice and unpaid status. Keep the order UUID.
4. Select the order and **Simulate payment**. Repeat it and check for `duplicate`. In **Membership**, verify **Awaiting RIWAY confirmation**. Verify that the order is on hold in **Compensation** as PH staff, and that neither the buyer nor SG staff can review the PH order. The PH reviewer without MFA should see the verification gate.
5. As **PH reviewer with MFA**, open **Membership review** and expand **Confirm an existing RIWAY record** on the matching order. Enter a unique synthetic member ID, sponsor `QA-BROWSER`, market `PH`, tier `SYNTHETIC_STARTER` and reference `SYNTHETIC-MANUAL`. Try the wrong sponsor first. The order stays on hold and the buyer stays pending. Correct the sponsor, confirm, and verify that the buyer sees the member ID and the hold clears. Use another order or one of the pre-seeded enrolments to exercise staff rejection independently.
6. Use **Reject compensation** to fail the next eligible event. The console shows the event and order IDs. Reload **Compensation** as PH staff, retry the failed row, then use **Acknowledge compensation** until the relevant paid event shows `acknowledged`. Use **Simulate compensation timeout** with another queued event and check the pending state, attempts and error in the console. Timeout uses the application’s normal backoff. Amount settlement and duplicate payment events must produce only one paid volume row per order.
7. As the buyer, request a return from the paid order. As PH staff, open **Returns**, find that exact order and approve a full refund with a synthetic reference. In the console select **Settle approved refund**. Reload the buyer’s order to verify the refunded status and check that the compensation reversal appears. Use **Acknowledge compensation** to process the reversal. If you settled the refund while the original paid event was still pending, the reversal must wait for the paid event’s acknowledgement. Try a separate partial refund to verify that only the approved amount is refunded and stock changes require a separate physical receipt.
8. For an unpaid case, create another order and use either the buyer’s cancel form or **Simulate expiry**. Verify that payment does not activate membership or create a paid compensation event. Expiry and cancellation release the stock reservation.

## Manual feature checklist

To test a replenishment schedule, approve a synthetic product and terms at **Staff schedule rules**. Use **Existing customer** to place and pay for a single **Synthetic qualifying goods** delivery order. From its order page start a schedule and review the terms. Try pause, resume and skip. In the console select **Make next renewal due**, open **Your schedules**, review the current quote and delivery address, then create the renewal order. Simulate expiry to exercise recovery, then retry and settle a new order. Verify sponsor continuity and that payment advances the due date. This path requires the buyer to approve and pay for every renewal.

To test a renewal reminder, approve the product's **Reminder lead days** in **Distributor tools** as PH staff. Enable the buyer's optional reorder email preference and make an active schedule due. Before creating an order, select **Check for due renewal reminders** in the sandbox console. The first run should queue one `replenishment_reminder` and the second none. An open renewal order, paused schedule, changed timing, refund or revoked consent suppresses a queued reminder before sending. The local sandbox records the notification without delivering email.
